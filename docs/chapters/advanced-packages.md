第43章では、`pubspec.yaml` を手で編集してパッケージを追加しました。
パッケージが増えると、追加の手間だけでなく、更新の方法や、利用条件の確認も必要になります。

## flutter pub addで追加する

`flutter pub add` を使うと、`pubspec.yaml` の編集と `flutter pub get` をまとめて実行できます。
プロジェクトのフォルダで次のコマンドを実行します。

```bash
flutter pub add dio
```

SDKのバージョンと整合する中で新しいバージョンが選ばれ、`pubspec.yaml` に次のような行が追加されます。

```yaml
dependencies:
  dio: ^5.9.0
```

バージョンを調べて書き写す手間と、インデントを間違えるおそれがなくなります。

開発時にだけ使うパッケージは `--dev` を付けて追加します。
第43章で説明した `dev_dependencies` に追加されます。
取り除くときは `flutter pub remove` を使います。

```bash
flutter pub add --dev flutter_launcher_icons
```

```bash
flutter pub remove dio
```

ネイティブのコードを含むパッケージを追加した後は、ホットリスタートでは反映されません。
`MissingPluginException` というエラーが出たら、アプリを停止して起動し直します。

## ^の意味

`^5.9.0` の `^` は、バージョン5.9.0と互換性があるはずの範囲を表します。
これを理解するには、パッケージのバージョン番号の付け方を知る必要があります。

パッケージのバージョンは、多くの場合、次の決まりで付けられます。
この決まりをセマンティックバージョニングと呼びます。

```text
5.9.0
│ │ └ パッチ：不具合の修正
│ └── マイナー：互換性を保った機能の追加
└──── メジャー：互換性のない変更
```

メジャーが変わると、これまでのコードが動かなくなる可能性があります。
そこで `^` は、次のメジャーの手前までを許可します。
ただし1.0.0より前は、まだ変更が多い段階とみなされ、範囲が狭くなります。

| 書き方 | 許可する範囲 |
| --- | --- |
| `^5.9.0` | 5.9.0以上、6.0.0未満 |
| `^0.14.4` | 0.14.4以上、0.15.0未満 |
| `5.9.0` | 5.9.0のみ |

`^` が保証するのは、選ばれるバージョンの範囲だけです。
範囲内の更新で必ず動くことまでは保証しません。
バージョン番号の付け方はパッケージの作者の判断に任されていて、不具合が混ざることもあるからです。

## pubspec.lockの役割

`^5.9.0` は範囲なので、これだけでは実際に使うバージョンが1つに決まりません。
実際に選ばれたバージョンは、自動で作られる `pubspec.lock` に記録されます。

```yaml
  dio:
    dependency: "direct main"
    description:
      name: dio
      sha256: "..."
      url: "https://pub.dev"
    source: hosted
    version: "5.9.0"
```

`pubspec.lock` には、`pubspec.yaml` に書いたパッケージだけでなく、それらが内部で使うパッケージも記録されます。
どのパッケージがどのパッケージに依存しているかは、`flutter pub deps` で一覧できます。

2つのファイルの役割は次のとおりです。

- `pubspec.yaml`：許可する範囲を開発者が書きます。
- `pubspec.lock`：実際に使う版をツールが記録します。手で編集しません。

`flutter pub get` は、`pubspec.lock` があれば、そこに書かれたバージョンを使います。
そのため、アプリを開発するときは `pubspec.lock` もコミットします。
コミットしておくと、チームの他の開発者や別のパソコンでも同じバージョンで動かせます。
コミットしていないと、新しくクローンした環境で別のバージョンが選ばれ、ある人の環境だけ動かないという問題が起きることがあります。

他の人に使ってもらうためのパッケージを作るときは、コミットしないことが推奨されています。
これは、さまざまなバージョンと組み合わせて使われるパッケージでは、最新の組み合わせでの動作を確認するほうが役に立つからです。

## パッケージを更新する

更新の候補は `flutter pub outdated` で確認できます。

```bash
flutter pub outdated
```

パッケージごとに、次の列が表示されます。

- `Current`：現在使っているバージョン
- `Upgradable`：`pubspec.yaml` を変更せずに更新できるバージョン
- `Resolvable`：`pubspec.yaml` の範囲を変更すれば更新できるバージョン
- `Latest`：公開されている最新のバージョン

更新のコマンドは2種類あります。

```bash
flutter pub upgrade
```

```bash
flutter pub upgrade --major-versions
```

前者は `pubspec.yaml` の範囲内で `pubspec.lock` を更新します。
後者はメジャーの更新のために `pubspec.yaml` の範囲も書き換えるので、コードの修正が必要になることがあります。
パッケージのページの `Changelog` で変更点を確認してから実行します。

更新したら、アプリを動かして確認し、更新だけのコミットを作ります。
機能の追加と分けておくと、問題が起きたときに第2章の `git diff` などで原因を絞り込みやすくなります。

## ライセンスを確認する

パッケージは他の人の著作物なので、作者が定めた条件に従って使います。
その条件を書いたものがライセンスです。
公開されていることは、自由に使ってよいことを意味しません。
ライセンスが書かれていないコードは、原則として著作権者の許可なしには利用できません。

pub.devのパッケージのページでは、右側の `License` の欄に種類が表示されます。
よく見かけるものは次のとおりです。

| ライセンス | 主な条件 |
| --- | --- |
| MIT、BSD-3-Clause | 著作権表示とライセンス文を含めれば、商用を含めて広く利用できます。 |
| Apache-2.0 | MITなどに近く、変更箇所の明示や特許についての条項もあります。 |
| GPL、AGPL | アプリを配布するときに、アプリ全体のソースコードを同じ条件で公開するよう求められることがあります。 |

ここに挙げたのは大まかな傾向です。
GPL系のパッケージは、組み込む前に条件をよく確認します。
ストアの利用規約との関係が問題になった例もあります。
仕事で使うアプリや判断に迷う場合は、原文を読み、所属する組織の担当者などに確認します。

確認の対象は、直接追加したパッケージだけではありません。
内部で使われているパッケージのライセンスも同じように適用されます。
また、画像やフォントはパッケージとは別に利用条件が定められています。

多くのライセンスは、アプリの中にライセンス文を含めることを求めます。
Flutterは、依存しているパッケージのライセンスを自動で集めて、一覧画面として表示する機能を持っています。

```dart
ElevatedButton(
  onPressed: () {
    showLicensePage(
      context: context,
      applicationName: 'メモアプリ',
    );
  },
  child: const Text('ライセンス'),
),
```

設定画面などからこの画面を開けるようにしておくと、一覧を確認できます。

## パッケージを信頼できるか

パッケージのコードは、自分のアプリの一部として、自分のアプリと同じ権限で動きます。
第43章で挙げた数字に加えて、次の点も確認すると判断の材料が増えます。

- 公開者の表示：pub.devで確認済みの公開者には、バッジが表示されます。
- 更新の頻度：長い間更新されていないと、新しいOSに対応できなくなることがあります。
- ソースコード：`Repository` のリンク先で、未解決の問題や開発の状況を確認できます。
- 本当に必要か：数行で書ける機能のために追加すると、更新と確認の対象が増えます。
